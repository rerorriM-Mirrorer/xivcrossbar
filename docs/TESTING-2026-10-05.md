# XIVCrossbar live test — build 0.4.0-a.20261005.8

This is the current checklist for the 16-file runtime overlay against
qEagleStrikerp/xivcrossbar `master` at `15d8381`. The overlay contains only
changed runtime files and `controller-extras.ini`; it has no `data` directory,
icons, tests or documentation. The working branch is
`work/consolidate-2026-10-04`. Its `master` remains the upstream baseline.

The offline Lua regressions and Lua 5.1 syntax checks pass after applying the
overlay to that exact fresh upstream checkout. Windows AHK input, actual FFXI
profiles and Windower drawing still need this live pass.

## Install and first login

1. Back up the currently enjoyed `xivcrossbar` folder if it has settings or
   bindings you want to keep. Exit any older XIVCrossbar experiment AHK script.
   With everyone logged out, install a fresh qEagleStrikerp `xivcrossbar`
   folder under `Windower/addons`, then extract the runtime overlay into
   `Windower/addons` so its 16 files merge into that folder. It is an overlay,
   not a complete addon.
2. Before loading, inspect `xivcrossbar/data`. The overlay does not contain
   that directory. If the fresh install has no character profiles, blank
   bindings on first login are expected; copy older profiles only if you want
   those bindings in this installation. Leave the old data backed up.
3. Log in on one character. Confirm the addon reports
   `0.4.0-a.20261005.8` and a `Profile: <server>/<character>` line in the
   Windower console. Check the actual new folder's server and character.
   Myrr's prior login created a blank Asura profile while her bindings lived
   elsewhere, so she is a useful regression case; any non-Asura character can
   reveal the same problem. An existing Asura folder is not proof of a new
   error—compare its modification time before and after login. Reload once and
   confirm the profile path and bindings are consistent.
4. Check the console's `Controller wrapper:` line after mapping setup. A raw
   DirectInput DualSense needs the DirectInput path; an emulated XInput pad
   needs XInput. Only one wrapper should be automatically started. Complete
   the original addon's gamepad mapping setup if this is a truly fresh install.

## Crossbar and display

1. Try `//xb ui status`; note the visibility mode, grace, scale, position and
   lock state. `//xb autohide on` should reveal on input and hide five seconds
   after release in a new configuration. `//xb ui grace 10` changes the wait;
   restore `//xb ui grace 5`. `//xb autohide off` leaves it visible. Existing
   per-character settings can override the fresh defaults.
2. With the bar hidden, run `//xb ui scale 0.75`. It should become visible for
   the configured grace period, then return to the prior mode. Try scale `0.8`
   and `1` too. Icons, labels, cost/recast text, indicators, and drag geometry
   should scale together. Check that a large icon such as Goring Blade stays
   within its frame. Look for text centering at both your small and large
   resolutions. `//xb ui aliasoffset 0 0` resets the alias adjustment.
3. Try `//xb ui unlock`. The Drag tile belongs at the right edge, with the
   right-aligned lock hint beneath the outline. Hover, drag, and check the
   restrained pink feedback and a visible one-pixel-or-more border at 75–80%
   scale. `//xb ui lock` should remove editing UI. Reload to check that the
   position persisted. `//xb ui hide` should hide the edit UI and prevent an
   invisible drag; `//xb ui auto` resumes automatic visibility.
4. During a cutscene, `//xb ui show` should reveal the bar on purpose; `auto`
   resumes event hiding. Check normal bound actions after toggling visibility.
   Compare reveal smoothness, but note that this build does **not** yet add the
   proposed fade animation.
5. Open the binder at a smaller resolution. Its background, title, choices and
   footer should stay centered together. Try `//xb ui menuscale 0.75` then `1`.
   Note any overlapping option text, clipping, or missing background. The old
   explanatory default-set notice is gone; fallback binding precedence is
   unchanged. Check sparse 3-, 4-, or 6-bar layouts if you already use them.

## Binding editor

1. On action-type and list screens, try the NEXT/PREV choices and L2/R2 page
   navigation. In a custom-action review screen, L2/R2 should also page. When
   choosing a *button combo*, the triggers still choose the destination bar;
   they do not page the menu.
2. In a spare slot, run `//xb ca new BowTest Friendly Bow`, then
   `//xb ca c input /bow`. From the review screen select **Save & Bind**, press
   a trigger plus button/d-pad combo, confirm, and try the new binding. Check
   that the catalog entry and slot use the same alias, command, and optional
   icon. Save Only should create a reusable catalog entry without binding it.
   Back after Save & Bind has already saved the catalog entry, even if you
   decide against assigning a slot.
3. Try an empty icon directory, a later icon-picker page, and Back navigation
   if you have suitable icons. A self-only action should not print the old
   `allow_stpc_for_self` diagnostic. Check that Basic, job default, all-jobs
   default and Shared still resolve as before with your own existing profiles.
   A fresh profile cannot establish whether prior bindings were preserved.

## Controller and multi-window

Controller extras revision `2026-10-05.1` adds the requested solo-window
toggle and delayed shoulder repeat. The Lua build number above is unchanged.
The prior tap-only shoulder behavior has a live pass reported on October 5;
the additions below still need their own live pass.

1. With at least two FFXI clients logged in, press and release L3. It should
   switch windows on release, once per press. R3 stays available for the native
   Run binding. Try pressing a trigger while holding L3; the focus switch
   should cancel. Close any standalone experimental AHK wrapper first.
   With exactly one client, L3 should minimize it when focused; another
   released press should activate/restore it from another program. Holding
   L3 must not switch before release. A focus change during the hold, or a
   change in client count during a solo press, should cancel it.
2. Focus FFXI, release both triggers and menu buttons, then press R1 once to
   cycle NPC targets forward with Tab. Press L1 once for reverse Shift+Tab.
   A short press should still send one tap. Hold either shoulder: after three
   seconds it should repeat twice per second. L1 keeps Shift held between taps
   and releases it when L1 is released. Switching focus, pressing a trigger or
   menu button, or disconnecting an XInput controller should cancel the hold
   and release the script's modifier. Refocusing while still held should not
   restart targeting until a new press. Neither shoulder should invoke a
   crossbar slot. The old
   DirectInput R1-to-F8 handler has been removed. This targeting path remains
   experimental until the live result is known.
3. If either extra is troublesome, set `ShouldersEnabled=0` or `L3Enabled=0`
   in `controller-extras.ini` beside the root AHK wrappers, then restart the
   active wrapper. DirectInput's measured numbers are L1=Joy5, R1=Joy6,
   L3=Joy11; XInput uses native button masks. When reporting a failure, note
   the console's selected wrapper, whether an older AHK process was active,
   the focused client, and the exact press/release order.
   `ShoulderRepeatEnabled=0` disables only repeat; taps still work.
   `SingleClientToggle=0` disables the solo toggle. Timing settings are
   `ShoulderRepeatDelayMs=3000` and `ShoulderRepeatIntervalMs=500`. Retain
   existing Joy mappings when adding these settings to your local INI.

## Report back

The most useful first report is: addon version; selected wrapper; character
and server profile path; whether the first fresh login created an unexpected
server folder; whether Save & Bind completed; and what R1/L1/L3 did. A screenshot
and console excerpt help for any clipping or Lua error. Keep the older data
backup until its bindings have been checked in the new installation.
